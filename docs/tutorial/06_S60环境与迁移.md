# 燧原 S60 环境与迁移

本章集中讲解燧原 S60。十题正文以海光 BW1000 为教学主线；S60 的设备接口、环境确认、逐题结果、参数变化、失败实验和 Task07 深入优化全部收录在这里。

S60 使用 torch_gcu 和 triton_gcu。最重要的迁移认识是：Triton 源码可移植，不等于 launch 参数、warp 数、整数表达式、归约策略和融合边界可以原样移植。

## 2. 环境确认不能只跑一个脚本

环境检查应按“设备节点 → 驱动 → Python 插件 → 张量执行 → Triton JIT”的顺序逐层进行。后一步通过不能替代前一步的信息记录。

### 2.1 第一层：设备、显存、温度和占用

```bash
efsmi
watch -n 1 efsmi
```

至少确认以下字段：

- `NAME` 是目标 S60，而不是其他燧原型号；
- Driver、Boot Firmware 与镜像配套；
- `Mem` 总量符合所申请的资源；
- `DUsed`、功耗和温度没有异常；
- 正式计时前没有其他进程持续占用设备。

`watch` 适合观察 benchmark 期间利用率是否真正拉起。若 Python 在运行但设备利用率一直为 0，应先怀疑张量仍在 CPU、JIT 未真正执行或进程在编译阶段。

### 2.2 第二层：操作系统与 Python 解释器

```bash
uname -a
cat /etc/os-release
which python
python --version
python -m pip --version
```

`which python` 和 `python -m pip` 必须属于同一个环境。不要用一个解释器运行、另一个解释器安装包。在线镜像通常已经把驱动、torch_gcu 和系统库配成一套，除非版本确实不符，不要直接升级系统 PyTorch。

### 2.3 第三层：四个关键 Python 包

```bash
python -m pip show torch torch-gcu triton triton-gcu
python - <<'PY'
import torch
import torch_gcu
import triton
import triton_gcu

print("torch      =", torch.__version__)
print("torch_gcu  =", torch_gcu.__version__)
print("triton     =", triton.__version__)
print("triton_gcu =", triton_gcu.__version__)
PY
```

四个包都能 import 只说明 Python 依赖存在，还没有证明设备可用或 Triton kernel 能编译。

### 2.4 第四层：torch.gcu 设备与显存分配

```bash
python - <<'PY'
import torch
import torch_gcu

print("available:", torch.gcu.is_available())
print("device_count:", torch.gcu.device_count())
print("current_device:", torch.gcu.current_device())
print("device_name:", torch.gcu.get_device_name(0))
print("properties:", torch.gcu.get_device_properties(0))

x = torch.arange(8, dtype=torch.float32, device="gcu")
y = x * 2 + 1
torch.gcu.synchronize()
print("result:", y.cpu().tolist())
print("allocated:", torch.gcu.memory_allocated(0))
print("reserved:", torch.gcu.memory_reserved(0))
PY
```

预期 `available=True`，设备数量大于 0，并得到 `[1,3,5,...,15]`。本项目显式使用 `device="gcu"` 和 `torch.gcu.synchronize()`；不要因为 torch_gcu 提供部分 CUDA 迁移补丁，就假设所有 `device="cuda"` 字面量都可靠。

### 2.5 第五层：确认 Triton target 与 warp size

```bash
python - <<'PY'
import torch
import torch_gcu
import triton

torch.empty(1, device="gcu")
target = triton.runtime.driver.active.get_current_target()
print(target)
print("backend:", target.backend)
print("arch:", target.arch)
print("warp_size:", target.warp_size)
PY
```

本机输出的 target 为 `dtu-enflame-tops--gcu300`，`warp_size=12`。这点非常重要：S60 的一个 Triton warp 是 12 lanes，不是 NVIDIA 常见的 32，也不能把海光配置中的 `num_warps=4` 机械理解成相同的线程组织。

`num_warps` 表示一个 Triton program 使用多少个目标后端 warp。增大它会同时改变执行资源、寄存器压力和后端调度，不是简单的“线程越多越快”。

### 2.6 第六层：手工验证真实 Triton JIT

下面的最小程序必须完成编译、launch、同步和 CPU 对比：

```python
import torch
import torch_gcu
import triton
import triton.language as tl


@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n: tl.constexpr, BLOCK: tl.constexpr):
    offsets = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
    mask = offsets < n
    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)
    tl.store(out_ptr + offsets, x + y, mask=mask)


n = 4096
x = torch.randn(n, device="gcu")
y = torch.randn_like(x)
out = torch.empty_like(x)
add_kernel[(triton.cdiv(n, 256),)](x, y, out, n=n, BLOCK=256)
torch.gcu.synchronize()
torch.testing.assert_close(out.cpu(), (x + y).cpu())
print("PASS Triton-GCU vector add")
```

仓库中的 `smoke_test.py` 封装了同一检查，但教程保留完整代码，是为了让读者知道脚本实际验证了什么，而不是把“脚本输出 PASS”误当成黑盒结论。

## 3. 设备选择与常用命令

S60 使用：

```bash
TOPS_VISIBLE_DEVICES=0 python program.py
```

`TOPS_VISIBLE_DEVICES` 必须在 Python 初始化 GCU 前设置。进程启动后再修改，可能导致设备枚举错误。

常用命令汇总：

```bash
# 设备状态
efsmi
watch -n 1 efsmi

# 包版本
python -m pip show torch torch-gcu triton triton-gcu

# 快速编译链检查
python platforms/enflame_s60/smoke_test.py

# 单题短回归
TOPS_VISIBLE_DEVICES=0 python evaluator/auto_bench.py \
  --v0_file platforms/enflame_s60/task07_mhc_post/reference.py \
  --v1_file platforms/enflame_s60/task07_mhc_post/solution.py \
  --warmup 5 --repeat 10

# 十题正式回归
WARMUP=200 REPEAT=500 \
  bash platforms/enflame_s60/run_all_benchmarks.sh
```

第一次运行包含 Triton 编译，不能把首次编译时间计入 kernel 性能。正式评测使用足够 warmup、每次同步并取中位数。

## 4. 为什么迁移到 S60 后会有算子变慢

Triton 是编写自定义 kernel 的工具，不是自动加速开关。S60 上的 PyTorch 基线也不是 Python 循环，而是 torch_gcu 背后的厂商优化库。

例如下面这些调用可能已经进入厂商融合或高性能实现：

```python
torch.einsum(...)
torch.nn.functional.scaled_dot_product_attention(...)
torch.nn.Linear(...)
torch.nn.LayerNorm(...)
```

自定义 Triton kernel 实际是在和厂商库竞争。是否加速取决于：

1. PyTorch 基线是否已经融合；
2. 问题规模能否摊薄 launch 成本；
3. tile 是否适合 S60 的 warp 与资源组织；
4. 中间张量是否真的被消除；
5. Triton-GCU 对该计算模式的代码生成是否成熟。

### 4.1 小问题规模：启动成本占比高

Task03 和 Task06 的序列长度只有 83。厂商 attention 已经在约 0.2～0.3 ms 内完成，自定义 kernel 的 launch、mask、地址计算和在线 Softmax 成本很难被摊薄。因此二者正确通过，但分别为 0.807× 和 0.818×。

### 4.2 厂商库边界：融合不一定减少总开销

Task04 的 Linear、GELU、LayerNorm 和 decoder 都有厂商实现。若自写 Triton 只替换其中一段，却额外产生中间张量或同步，整体可能更慢。S60 最终采用厂商矩阵/归一化算子加 Triton 池化，正确但为 0.597×。

### 4.3 海光参数不能直接搬过来

Task06 的海光配置为 64 行 tile、4 warps，直接迁移到 S60 约 9.88 ms；改为 32 行 tile、1 warp 后正式为 0.335449 ms。Task03 从 1 warp 改成 4 warps，也会从约 0.29 ms 退化到约 3.88 ms。

这与 S60 后端报告的 `warp_size=12` 密切相关。不同平台的 `num_warps=4` 并不代表相同的执行宽度、占用率或寄存器压力。

### 4.4 当前后端的功能与稳定性边界

- Task04 的原二维 launch 需要 `grid.y=477`，超过当前后端限制，必须展平 program id；
- Task10 的 `offsets & 3` 会段错误，改成数学等价的 `offsets % 4` 后稳定；
- Task10 的宽 `tl.sum` 和 FP32 atomic 路径实测不稳定；
- 二维 block 张量、宽向量和大量 program 的组合对性能异常敏感。

这些不是“改个 warp 数”就一定能解决的问题，需要改变 program 映射或重新划分厂商算子与 Triton kernel 的边界。

## 5. Task07 深入分析：从 29.46 ms 降到 5.82 ms

Task07 的公式是：

```text
out[row,n,h] = x[row,h] * post[row,n]
             + Σ residual[row,m,h] * comb[row,m,n]
```

其中 row=8192、n=m=4、hidden=1280。海光上把固定 4×4 完全展开很有效，但相同的全 Triton kernel 在 S60 上正式耗时 29.462086 ms。

### 5.1 先拆开 PyTorch 基线

对参考实现分段测量得到：

| 部分 | S60 中位耗时 |
| --- | ---: |
| `residual.float()` | 约 0.694 ms |
| 4×4 batched `einsum` | 约 1.689 ms |
| `x × post` 广播 | 约 0.799 ms |
| 缓存结果的 add + BF16 cast | 约 1.825 ms |
| 完整参考实现 | 约 4.128 ms |

这说明厂商 `einsum` 并不慢。真正错误的假设是“4×4 很小，所以通用 einsum 一定比手工展开慢”。这个判断在海光成立，在 S60 上不成立。

### 5.2 失败实验告诉了我们什么

| 实验 | 短测耗时 | 结论 |
| --- | ---: | --- |
| 原全 Triton，1 row/program，2048 hidden tile | 约 29.6 ms | 正确，但寄存器状态和四路输出代价高 |
| hidden 拆成 256，多 program | 约 36.9 ms | program 数增加和系数重复加载抵消收益 |
| 4 rows × 256 hidden 的二维 tile | 约 80.0 ms | 后端对二维 block 表达生成质量较差 |
| 每个输出 channel 单独一个 program | 约 48.3 ms | 降低寄存器压力，却四次重复读取 residual |
| 厂商 einsum + Triton epilogue，4 warps | 约 15.6 ms | 融合边界正确，但 warp 数仍不合适 |
| 厂商 einsum + Triton epilogue，1 warp | 约 5.6～5.8 ms | 当前最佳稳定方案 |

性能实验不能只保留赢家。失败配置帮助确定瓶颈来自二维 block、重复 program、寄存器压力以及 warp 调度的组合，而不是单纯的显存带宽。

### 5.3 最终融合边界

最终方案让 torch_gcu 执行擅长的 batched `einsum`，Triton 负责融合：

```text
x × post + term2 + BF16 cast
```

Triton epilogue 一个 program 处理一个 row，用 2048 元素向量覆盖 1280 hidden，并使用 `num_warps=1`。这样既保留了真正有意义的自定义融合，也避免用 Triton 重写当前后端已经很快的 4×4 contraction。

正式 200/500 结果：

```text
PyTorch: 4.213931 ms
Triton : 5.820457 ms
Speedup: 0.724x
```

它仍未反超厂商完整实现，但比旧 Triton 的 29.462086 ms 快约 5.06 倍。这里应记录真实边界，而不是用空 kernel 包装完整 PyTorch 路径来制造“使用了 Triton”的表象。

## 7. 推荐的 S60 迁移流程

1. 用 `efsmi` 确认型号、驱动、显存、占用和温度。
2. 记录 Python 解释器及 torch/torch_gcu/Triton/triton_gcu 四个版本。
3. 用 `torch.gcu` 完成张量运算和同步验证。
4. 查询 Triton target 与 `warp_size`，不要套用 CUDA/海光线程直觉。
5. 手工运行最小 Triton kernel，证明 JIT 和设备执行链真实可用。
6. 使用 `warmup=1/repeat=3` 建立逐题正确性基线。
7. 分段测量 PyTorch 参考实现，先找出厂商库已经很快的部分。
8. 一次只改变融合边界、tile 或 `num_warps` 中的一项。
9. 遇到段错误，先缩小 tile、去掉宽归约/atomic，并把位运算换成普通整数运算。
10. 固定最终源码后，以 200/500 完整回归并保留所有未加速项。

平台代码和复现入口见 GitHub 上的 [S60 平台说明](https://github.com/mantuoluozk/kernelswift-2026-triton-kernels/blob/main/platforms/enflame_s60/README.md)。
