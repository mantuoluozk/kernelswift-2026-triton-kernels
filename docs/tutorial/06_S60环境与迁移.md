# 燧原 S60 环境与迁移

S60 使用 torch_gcu 和 triton_gcu。对初学者最重要的认识是：Triton 源码可移植，不等于 launch 参数、整数表达式和归约策略可原样移植。

## 环境确认

```bash
efsmi
python -m pip show torch torch-gcu triton triton-gcu
python platforms/enflame_s60/smoke_test.py
```

设备接口使用 `gcu`：

```python
import torch
import torch_gcu

x = torch.randn(1024, device="gcu")
torch.gcu.synchronize()
```

选择逻辑卡时在进程启动前设置：

```bash
TOPS_VISIBLE_DEVICES=0 python program.py
```

日常监控使用 `efsmi` 或 `watch -n 1 efsmi`，同时关注利用率、显存、温度和占卡进程。

## 为什么必须重新调 `num_warps`

`num_warps` 不是“越大并行越多、所以越快”。它还改变一个 program 的资源分配和后端调度。S60 上 Task03 使用 1 warp 时正式耗时 0.286620 ms；改成 4 warps 的短测约 3.88 ms。Task06 也从海光的 64 行/4 warp 调为 32 行/1 warp，才从约 9.88 ms 降到正式 0.335449 ms。

因此迁移流程应该是：先保持数学映射不变，再独立扫描 tile 与 warp 数；每次修改都重新做精度检查。

## grid 维度限制

Task04 原始二维 launch 的第二维需要 477 个 block，而当前 S60 后端只接受较小的 `grid.y`。解决方法不是减少 vocab 覆盖，而是把两个维度展平：

```python
n_blocks = triton.cdiv(vocab_size, block_n)
grid = (segments * n_blocks,)
```

kernel 内再通过除法和取模恢复 `segment` 与 `vocab_block`。这是一种通用的后端兼容技巧。

## 段错误的最小化排查

Task10 展示了一个容易误判的问题：`offsets & 3` 与 `offsets % 4` 在数学上等价，但前者在当前后端会段错误，后者稳定通过。宽 `tl.sum` 和 FP32 atomic 组合也出现不稳定。

排查时应逐层缩小：

1. 把多阶段 kernel 拆开，确认崩溃发生在哪一次 launch；
2. 减少 `BLOCK_SIZE`，去掉归约和 atomic，只保留逐元素链；
3. 把位运算改成普通整数运算；
4. 再逐个恢复优化，并每次单独启动新 Python 进程验证。

最终 Task10 由 Triton 融合 sigmoid 反向的逐元素计算，torch_gcu 完成末级小归约，正式达到 1.197×。

## 正确但未加速同样有价值

Task07 的全 Triton 实现正确通过，但正式只有 0.142×。把 hidden tile 从 2048 拆成 256 后 program 数增加，性能还会继续下降。这说明厂商 `einsum` 已有高效实现，而当前 Triton 后端对该大张量 launch/向量映射仍不理想。

教程保留真实结果，因为它给出了比“所有算子都加速”更重要的工程判断：

- 先证明语义和跨后端可运行；
- 再用 profile 判断瓶颈是否在访存、program 数或代码生成；
- 逐题排名，不用简单合计替代算子级结论；
- 没有稳定收益时记录边界，而不是用无关的空 kernel 包装厂商实现。
