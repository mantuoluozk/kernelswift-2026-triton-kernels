## 2. 为什么代码里仍然出现 `torch.cuda`

当前 DTK PyTorch/Triton 兼容环境沿用了 PyTorch 的 CUDA 风格设备接口，因此代码使用 `.cuda()`、`torch.cuda.synchronize()` 和 `device="cuda"`。这不意味着底层运行的是 NVIDIA CUDA；实际后端由 DTK/HIP 栈完成。

不要因为接口名字相同，就假定所有 CUDA 硬件细节都一模一样。尤其是 wavefront 宽度、矩阵指令、寄存器分配和最优 tile，都必须在 BW1000 上实测。

## 3. 选择空闲卡

先查看设备占用，再用 `HIP_VISIBLE_DEVICES` 限制当前进程可见设备：

```bash
hy-smi --showmeminfo vram --showuse
HIP_VISIBLE_DEVICES=0 python3 benchmark.py
```

DTK 26.04 开发环境手册明确说明，`HIP_VISIBLE_DEVICES=0,3` 可把程序限制到第 1、4 张 DCU。比赛计分按芯片型号，而不是同一机器中的物理卡号；多张 BW1000 只用于并行实验或复现性检查。

## 4. 正确性检查必须先于性能

基本流程：

```python
expected = reference(*inputs)
actual = optimized(*inputs)
torch.cuda.synchronize()
torch.testing.assert_close(actual, expected, atol=1e-2, rtol=1e-2)
```

对离散输出不能只用 `assert_close`。例如 Task01 的专家 ID 必须用 `torch.equal` 比较；浮点权重再单独用容差比较。对 tuple/list 输出，要逐项检查。

### 4.1 为什么结果不必逐位相等

浮点加法不满足严格结合律：

```text
(a + b) + c 可能不等于 a + (b + c)
```

Triton 改变归约树或把 FP16/BF16 输入提升为 FP32 累加后，最低位可能变化。应该记录：

- 最大绝对误差；
- 最大相对误差；
- 是否包含 NaN/Inf；
- 离散结果是否完全一致。

容差是验收边界，不是随意降低精度的许可。必须解释误差来自数据类型、舍入还是运算顺序。

## 5. 正确的性能测量

设备 kernel 异步执行。只测 Python 调用前后的 CPU 时间而不同步，会把“提交任务”误当成“完成计算”。本项目使用：

```python
for _ in range(warmup):
    fn()
torch.cuda.synchronize()

samples = []
for _ in range(repeat):
    start = time.perf_counter()
    fn()
    torch.cuda.synchronize()
    samples.append((time.perf_counter() - start) * 1e3)

median_ms = statistics.median(samples)
```

### 5.1 Warmup 的作用

第一次调用可能包含 Triton JIT 编译、模块加载、缓存建立和内存分配器初始化。warmup 把这些一次性成本排除在稳定执行时间之外。

### 5.2 为什么取中位数

共享服务器会有调度抖动、其他进程干扰和偶发缓存波动。中位数比平均数更不容易被少量异常慢样本拉高。本项目正式记录使用 `warmup=200`、`repeat=500`。

### 5.3 公平比较清单

- reference 与 solution 使用同一输入；
- 有参数的模型使用同一 `state_dict`；
- 随机算子在两次调用前重置同一 seed；
- 两边都在 `torch.no_grad()` 下运行；
- 输出分配和必要的数据类型转换是否都处在同一计时边界；
- 不把编译时间混入稳态时间；
- 不通过 fallback 绕过自定义 kernel。

## 6. 参数扫描

不要只测试一次。典型扫描维度包括：

```text
num_warps ∈ {1, 2, 4, 8}
BLOCK_SIZE ∈ {256, 512, 1024, 2048}
BLOCK_M/BLOCK_N/BLOCK_K 的若干组合
```

每次只改变一个因素，记录正确性、耗时和显存。小任务使用更多 `num_warps` 不一定更快，因为并行资源和寄存器开销也会增加；Task01/08/09 最终都选择了 1，而 Task05/10 分别选择 8。

## 7. 使用 hipprof 建立证据

DTK 26.04 的 hipprof 手册建议先用 trace 定位热点，再用 PMC 分析指定 kernel：

```bash
hipprof --pmc ./your_program
hipprof --pmc --kernel-name "kernel_name" ./your_program
hipprof --pmc --pmc-type 3 ./your_program
```

关注指标包括 kernel time、work-group size、VGPR/SGPR、共享内存、L1/L2 活跃与停顿、L2 命中率以及共享内存 bank conflict。寄存器压力过高会降低同时驻留的 wave 数，甚至产生 scratch/local memory 访问。

Python/Triton 场景中 kernel 名称可能较长，可先 trace 一次找到实际名称，再用 `--kernel-name` 过滤。若工具版本无法直接解析 JIT code object，至少使用 trace 的 kernel 数量与耗时判断融合是否生效。
