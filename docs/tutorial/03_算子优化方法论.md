# 03：从 PyTorch 参考实现到高性能 kernel

## 1. 第一步不是写代码，而是冻结契约

先记录：

- `Model.__init__` 参数；
- `forward` 参数顺序；
- 输入输出形状、dtype、device 和布局；
- 参数/buffer 名称，是否需要 `state_dict` 对齐；
- 随机数调用顺序；
- 容差和离散输出要求。

比赛评测通常会用参考模型参数覆盖优化模型。如果 Task02/04 改了 `w1`、`decoder.weight` 等名称或形状，即使 kernel 数学正确也无法评测。

## 2. 把计算图写成中间张量表

以 Task04 为例：

| 阶段 | 输出形状 | 潜在代价 |
| --- | --- | --- |
| dense | `[83,768]` | GEMM |
| GELU | `[83,768]` | 读写一次完整张量 |
| LayerNorm | `[83,768]` | 多次归约与读写 |
| decoder | `[83,30522]` | 大 GEMM、巨大输出 |
| ReLU+log1p | `[83,30522]` | 再次读写巨大输出 |
| segment max | `4×[30522]` | 再读 logits |

看到表后，优化方向自然出现：融合 GELU+LayerNorm；把 decoder 输出直接送入 segment max，避免物化大 logits。

## 3. 先判断瓶颈类别

### 3.1 Launch-bound

特征：张量很小，但 PyTorch 调用了很多操作；单个 kernel 计算量不大。Task08 的 20 轮 Sinkhorn、Task10 的多个逐元素与归约属于此类。首选策略是融合。

### 3.2 Memory-bound

特征：每个元素计算少，主要成本是读写显存。Task05 的广播/拼接/三角函数链和 Task07 的大型中间张量明显受内存流量影响。首选策略是一次加载、多次复用、直接写最终输出。

### 3.3 Compute-bound

特征：大量乘加，`tl.dot` 或库 GEMM 占主要时间。Task02/04 的投影属于此类。首选策略是合理 tile、低精度乘法+高精度累加、减少无用计算并把 epilogue 融入。

### 3.4 混合型

Attention 既包含 QK/PV 计算，又会产生平方级 score/probability 矩阵。在线 Softmax 同时减少中间内存和保持矩阵计算，是典型混合优化。

## 4. 融合的本质：缩短数据的“片外旅程”

设某中间张量有 `N` 个 FP32 元素。如果先写回再读入，至少多出：

```text
N × 4 字节写 + N × 4 字节读 = 8N 字节
```

如果中间值能留在寄存器/片上存储中，就能省掉这段流量和一个或多个 launch。DTK 手册强调寄存器访问快、适合保存频繁复用的线程私有数据，但也提醒寄存器过多会溢出并降低 occupancy。因此融合不是越大越好：Task02 保留三个规则化阶段，而没有强行做成一个巨大 kernel。

## 5. 数学等价变换比微调 block 更重要

### 5.1 单调函数与 max/top-k

若 `f` 严格单调递增，则：

```text
argmax f(x) = argmax x
max f(x) = f(max x)
topk(f(x)) 的索引与 topk(x) 相同
```

应用：

- Task01 在 logits 上选择组和专家，不先算完整 Softmax；
- Task04 把 `log1p(ReLU(.))` 移到 max pooling 之后。

移动运算前必须证明单调区间和操作类型。`sum(f(x))` 一般不能改成 `f(sum(x))`。

### 5.2 公共因子抵消

Task01 中：

```text
softmax(l_i) = exp(l_i) / Z
```

对选中的 8 项再次归一化：

```text
(exp(l_i)/Z) / Σ_j(exp(l_j)/Z) = exp(l_i) / Σ_j exp(l_j)
```

公共分母 `Z` 抵消，因此不需要计算 256 路 Softmax 分母。

### 5.3 在线 Softmax

把列分块处理。已有状态为最大值 `m_old`、指数和 `l_old`、加权输出 `acc_old`，新块最大值为 `m_blk`：

```text
m_new = max(m_old, m_blk)
alpha = exp(m_old - m_new)
p_blk = exp(score_blk - m_new)
l_new = alpha * l_old + sum(p_blk)
acc_new = alpha * acc_old + p_blk @ V_blk
```

最后 `out = acc / l`。这使 Attention 无需保存完整 score 和 probability 矩阵。

## 6. 选择 program 粒度

经验问题：哪些数据应被同一个 program 复用？

- 一行元素一起归约：一个 program 一行，如 Task01；
- 一个小矩阵迭代多轮：一个 program 一个矩阵，如 Task08；
- 一个 batch/head 的 query tile 共享 K/V 流：一个 program 一个 query tile，如 Task03/06；
- 一个 `(batch,token)` 的四路输出共享输入：一个 program 一行，如 Task07；
- 一个增强样本共享同一旋转和平移：一个 program 一个 sample，如 Task09。

粒度太小会重复加载和增加 launch/program 数；粒度太大则会增加寄存器压力、降低并发。

## 7. 合并访存

DTK 最佳实践的结论是：让连续执行线程访问连续地址。Triton 中对应做法是把 `tl.arange` 放在物理连续的内层维度。

```python
hidden = block * BLOCK + tl.arange(0, BLOCK)
ptrs = base + row * hidden_size + hidden
```

Task07/10 都沿最后一维连续访问。跨距访问会让一次 wave 的地址分散，显存事务利用率下降。

## 8. 数据类型策略

常见组合：

- 输入 FP16/BF16；
- `tl.dot` 使用 FP16 输入；
- accumulator、Softmax 状态和归约使用 FP32；
- 最终 store 自动或显式转换到输出 dtype。

Task07 的输出是 BF16，但计算表达式参考实现先转 FP32。优化 kernel 读 BF16 后在表达式中提升并累加，最终写 BF16。不同累加顺序导致小误差，需要用官方容差验证。

## 9. 什么时候不要继续融合

- 融合后块张量过大，VGPR 暴涨或发生 spill；
- 两阶段之间的数据量已经很小；
- 独立 GEMM 库/kernel 已经高度优化，融合会破坏矩阵指令使用；
- 不同输出分支几乎不共享数据；
- 需要原子操作或跨 program 全局同步，复杂度超过收益。

Task02 的三阶段设计就是折中：规则化计算所有专家看似多算了一些，但避免了动态布尔分发和大量极小 GEMM；若强行把两层专家网络、路由和所有 token 放入单 kernel，寄存器状态会过大。

## 10. 调优实验记录模板

```markdown
### 假设
reference 慢在 20 轮小 kernel launch，而不是算术量。

### 改动
一个 program 保存 4×4 矩阵并完成全部迭代。

### 正确性
max_abs_diff = ...，atol/rtol = ...，PASS。

### 性能
BLOCK/num_warps = ...；中位数 ... ms；加速比 ...x。

### 结论
kernel 数下降；继续增大 num_warps 无收益，说明块内工作量太小。
```

不要只保留最快数字，也记录失败配置和原因。下一次遇到相似形状时，这些失败数据往往比最终答案更有价值。
