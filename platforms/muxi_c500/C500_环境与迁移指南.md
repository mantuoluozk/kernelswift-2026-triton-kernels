# 沐曦 C500 环境与 Triton 迁移指南

这份指南面向已经熟悉海光 BW1000、DTK、HIP 和 `hy-smi`，但第一次使用沐曦 C500/MXMACA 的开发者。命令以当前模力方舟 C500 实例实测结果为准。

## 1. 先建立概念映射

| 海光经验 | 沐曦 C500 对应物 | 本项目中的意义 |
| --- | --- | --- |
| DTK / ROCm 软件栈 | MXMACA / MACA 软件栈 | 驱动、运行时、编译器和数学库的总称 |
| `hy-smi` | `mx-smi` | 查设备、利用率、显存、进程、功耗和温度 |
| DCC / `hipcc` | `mxcc` | C/C++ GPU 编译器；本比赛主要由 mcTriton JIT 调用后端 |
| HIP Runtime | MXMACA Runtime | 设备、内存、stream、kernel launch 等运行时能力 |
| rocBLAS / hipBLASLt | mcBLAS / mcBLASLt | GEMM 和矩阵计算库 |
| MIOpen | mcDNN | 深度学习原语库 |
| RCCL | MCCL | 多卡通信库 |
| hipprof | mcTracer / mcProfiler | tracing 和性能分析工具 |
| ROCm Triton 后端 | mcTriton | 上游 Triton 加 MXMACA 后端 |
| `HIP_VISIBLE_DEVICES` | `CUDA_VISIBLE_DEVICES` | mcPyTorch 沿用 CUDA 兼容接口；当前切片实例只有一个逻辑设备 |
| `torch.cuda` 在海光兼容层可用 | `torch.cuda` 在 mcPyTorch 中可用 | 代码仍写 `cuda:0`，设备名实际返回 MetaX C500 |

最重要的认知是：Triton Python 源码大部分能复用，但底层 compiler lowering、warp 映射、矩阵指令、寄存器压力和某些广播/归约组合并不等价。因此“能编译”不等于“数值正确”，“在 BW1000 最优”也不等于“在 C500 最优”。

## 2. 当前实例是什么

`mx-smi` 显示物理 C500 有 65536 MiB，但本实例是一个 25% sGPU：

```text
GPU 0: MetaX C500
Physical memory: 65536 MiB
sGPU compute quota: 25%
sGPU VRAM quota: 16000 MiB
PyTorch total_memory: about 15584 MiB
```

所以调优时要同时考虑两个限制：只有约四分之一计算资源，以及只有约 16 GB 的显存配额。与整卡公开成绩不能直接横向比较。

实例的 `/data` 是持久化盘，根文件系统只有约 30 GB，代码、模型、日志和大缓存应放 `/data`。实例到期或欠费可能被销毁，重要代码要及时推送 Git 仓库。

当前模力方舟实例本身已经运行在容器中，内部没有 Docker CLI，也不需要像海光服务器那样执行 `docker_create.sh` 再进入一层开发容器。

## 3. 环境初始化

### 3.1 交互式登录

当前镜像的 `/root/.bashrc` 已配置 Conda、MACA 路径并默认进入 `/data`。登录后先检查：

```bash
which python
python --version
echo "$MACA_PATH"
mx-smi -L
```

预期 Python 是 `/opt/conda/bin/python`，`MACA_PATH=/opt/maca`。

### 3.2 非交互命令和自动化脚本

`ssh host "python ..."` 通常不会加载交互式 `.bashrc`。如果看到：

```text
ModuleNotFoundError: No module named 'torch'
OSError: libmpi.so.40: cannot open shared object file
```

不代表包没安装，而是用到了 `/usr/bin/python3` 或缺少动态库路径。执行：

```bash
source /data/zk/kernelswift-2026-triton-kernels/platforms/muxi_c500/setup_env.sh
```

脚本内容保留为普通 shell 环境变量，方便在别的 C500 容器中复制和审计。

### 3.3 版本必须成套

```bash
python -c "import torch,triton; print(torch.__version__); print(triton.__version__)"
pip list | grep -Ei 'torch|triton|metax'
cat /opt/maca/Version.txt
mx-smi --show-version
```

当前组合是 MACA 3.0.0.8、mcPyTorch 2.4.0+metax3.0.0.3、mcTriton 3.0.0+metax3.0.0.3。不要直接执行：

```bash
pip install -U torch triton
```

普通 PyPI wheel 没有 MXMACA 后端，且可能破坏厂商匹配的动态库组合。升级必须使用同一套沐曦发布包或平台镜像。

## 4. `mx-smi` 常用命令

### 4.1 一眼看全局

```bash
mx-smi
mx-smi -s
mx-smi -L
```

- `mx-smi`：设备摘要、利用率、功耗、温度、显存和进程。
- `mx-smi -s`：summary。
- `mx-smi -L`：只列设备。

### 4.2 连续监控

```bash
mx-smi -l 1000
mx-smi --show-usage --show-memory --show-temperature --show-board-power -l 1000
```

`-l` 单位是毫秒，按 `Ctrl+C` 停止。跑 benchmark 时另开一个 SSH 窗口观察，主要看：

- GPU-Util 是否持续上升；
- Memory-Usage 是否逼近 16000 MiB 切片配额；
- 温度和功耗是否稳定；
- GPU-State 是否为 Available。

小算子单次只有 0.1 ms 左右，1 秒采样可能看不到尖峰。应增加 repeat、用循环压测，或使用 profiler，而不能仅凭 `mx-smi` 的 0% 判断 kernel 没运行。

### 4.3 分项查看

```bash
mx-smi --show-usage
mx-smi --show-memory
mx-smi --show-process
mx-smi --show-all-process
mx-smi --show-temperature
mx-smi --show-board-power
mx-smi --show-hbm-bandwidth
mx-smi --show-pcie-bandwidth
mx-smi --show-clocks all
mx-smi --show-dpm cur
mx-smi --show-version
mx-smi --show-hwinfo
```

指定卡：

```bash
mx-smi -i 0 --show-memory --show-usage
```

导出 CSV：

```bash
mx-smi --show-usage --show-memory --show-temperature -l 1000 -o mxsmi.csv
```

不要照搬 NVIDIA 的 `nvidia-smi -q`；当前 `mx-smi` 没有 `-q`，使用明确的 `--show-*` 参数。

### 4.4 高风险管理命令

`--kill-all-process`、`--reset`、`--flr`、`--vfflr`、固件升级、ECC/功耗/DPM 设置都可能中断作业或影响整卡。在共享平台和 sGPU 实例中不要自行执行，除非平台管理员明确授权。

## 5. PyTorch 与显存检查

### 5.1 最小健康检查

```bash
python - <<'PY'
import torch
print('torch:', torch.__version__)
print('available:', torch.cuda.is_available())
print('count:', torch.cuda.device_count())
print('name:', torch.cuda.get_device_name(0))
print('capability:', torch.cuda.get_device_capability(0))
print('properties:', torch.cuda.get_device_properties(0))
x = torch.arange(16, device='cuda', dtype=torch.float32)
print((x * x).cpu())
PY
```

`get_device_capability()` 返回的兼容能力值用于 CUDA 兼容生态判断，不应当直接当成 NVIDIA SM 架构来推导 C500 硬件细节。

### 5.2 PyTorch 进程内显存

```python
import torch

print(torch.cuda.mem_get_info())
print(torch.cuda.memory_allocated())
print(torch.cuda.memory_reserved())
print(torch.cuda.max_memory_allocated())
print(torch.cuda.memory_summary())
torch.cuda.reset_peak_memory_stats()
```

- `allocated`：活跃 tensor 实际占用；
- `reserved`：PyTorch caching allocator 向设备保留；
- `mx-smi`：整个进程/context 的设备占用，通常比 allocated 更大。

`torch.cuda.empty_cache()` 只释放未被 tensor 使用的缓存块，不会释放仍被引用的 tensor，也不能解决真正的显存泄漏。

### 5.3 选择设备

```bash
CUDA_VISIBLE_DEVICES=0 python your_script.py
```

当前实例只有一个逻辑 sGPU，通常不需要设置。多卡物理机可使用该变量；不要混用海光项目脚本中的 `HIP_VISIBLE_DEVICES`。

## 6. Triton 开发和测量

### 6.1 mcTriton 仍使用标准 Python API

```python
import triton
import triton.language as tl

@triton.jit
def kernel(...):
    ...
```

但必须把 kernel 放在真实 `.py` 文件中。通过 `python - <<'PY'` 临时定义时，Triton 3.0 可能因 `inspect.getsourcelines()` 无法取得源文件而报 `OSError: could not get source code`。

### 6.2 正确测时

- 先 warmup，避免把首次 JIT 编译计入时间；
- 每次计时前后保持输入、随机种子和同步规则一致；
- GPU 调用异步，计时边界必须 `torch.cuda.synchronize()`；
- 比较中位数，不用单次耗时；
- 小 kernel 要足够多的 repeat。

本仓库统一使用：

```bash
python evaluator/auto_bench.py --v0_file reference.py --v1_file solution.py \
  --warmup 200 --repeat 500
```

### 6.3 Triton 缓存

当前缓存位于：

```bash
du -sh /root/.triton
find /root/.triton/cache -maxdepth 1 -type d | head
```

怀疑编译缓存异常时，先退出所有相关 Python 进程，再只删除缓存内容：

```bash
find /root/.triton/cache -mindepth 1 -maxdepth 1 -type d -exec rm -rf -- {} +
```

下一次运行会重新 JIT，明显变慢属于正常现象。不要在 benchmark 计时过程中清缓存。

### 6.4 调参优先级

从海光实现迁移时，不要一次改很多项。建议顺序：

1. 先用很短的 warmup/repeat 验证正确性和是否 crash；
2. 固定算法，只扫 `BLOCK_SIZE/BLOCK_M/BLOCK_N/BLOCK_K`；
3. 再扫 `num_warps`；
4. 检查寄存器压力、并行 program 数和访存合并；
5. 最后才改变算法或引入 `tl.dot`/更深融合；
6. 用正式 200/500 参数复验。

## 7. 从 BW1000 迁移十个算子的差异

| 任务 | C500 首轮结果 | 与海光实现的主要差异或下一步 |
| --- | --- | --- |
| Task01 GroupedTopk | 直接通过，3.33x | 小规模排序/归约逻辑可复用；`num_warps=1` 在 C500 仍有效 |
| Task02 FusedMoE | 直接通过，19.12x | 三阶段融合和 tile GEMM 可复用；C500 对 MoE/GEMM 路径表现好，后续重点扫矩阵 tile |
| Task03 FlexAttention | 通过，但仅 1.26x | 在线 softmax 算法可复用；C500 上 16×32 tile 和单 warp 未必最优，应扫 query/key tile 与 warps |
| Task04 SPLADE | 通过，2.52x | FP16 `tl.dot` 和融合策略可复用；C500 矩阵指令后端不同，`BLOCK_N/K=64` 需重新搜索 |
| Task05 Rotary | 直接通过，2.43x | 纯逐元素融合最易迁移；仍需检查 1024 block、8 warps 是否寄存器过重 |
| Task06 MM Attention | 通过，但仅 1.29x | 与 Task03 类似，算法正确但海光 tile 不是 C500 最优参数 |
| Task07 mhc_post | 通过，16.75x | mcPyTorch 默认把 4D CPU 输入转为 channels-last；设置 `PYTORCH_DEFAULT_NCHW=1` 后复用海光高性能 kernel |
| Task08 Sinkhorn | 原实现段错误，已修复 | C500 Triton 3.0 在 4×4 二维 `arange` 广播加跨轴 reduction 组合上崩溃；显式标量化 16 个元素后通过，0.164 ms、14.23x |
| Task09 Augmentation | 直接通过，6.16x | 随机调用顺序和单 program 归约可复用；C500 上表现优于海光短基线 |
| Task10 backward | 通过，1.65x | 大 block 全局归约可复用，但 8 warps 需重扫，目标是减少 launch/归约开销 |

### 7.1 为什么 Task08 要标量化

海光版本使用：

```python
offsets = row[:, None] * 4 + col[None, :]
x = tl.load(... + offsets)
row_sum = tl.sum(x, axis=1)
col_sum = tl.sum(x, axis=0)
```

数学上很自然，但当前 C500 mcTriton 后端对这个极小二维张量的广播和双轴归约 lowering 会触发进程段错误。因为矩阵固定只有 4×4，显式保留 `m00...m33`，手写四个行和、四个列和，既规避编译器问题，也不会造成不可接受的代码规模。

这里的迁移原则是：固定尺寸极小张量遇到后端 compiler bug 时，标量化是合理的工程方案；尺寸较大时则不能照搬，否则会导致代码膨胀和寄存器爆炸。

### 7.2 Task07 为什么不是公式错误

mcPyTorch 为优化 4D Tensor，会在 CPU→device 搬运时默认转换为 channels-last。张量的逻辑 shape 不变，但 stride 会从普通 NCHW 变为类似 `(N, 1, ..., C)` 的布局。PyTorch 算子理解这些 stride，而不接收 stride 参数、直接做线性指针运算的 Triton kernel 会读错数据。

官方提供的兼容开关是：

```bash
export PYTORCH_DEFAULT_NCHW=1
```

本平台的 `setup_env.sh` 已设置该变量。Task07 还用一维输出缓冲区让 Triton 写回，再 `view` 成目标 4D shape。这个案例说明跨后端排错时应先打印 `shape/stride/is_contiguous/memory_format`，不要只检查数值公式。

### 7.3 为什么 Task03/06/10 要重新扫参数

这些任务都已经正确，但加速比低于海光。原因不一定是 C500 算力弱，而可能是：

- sGPU 只有 25% 计算配额；
- program tile 数量不够，无法填满当前切片；
- `num_warps` 到实际执行资源的映射不同；
- attention 的矩阵 tile 没匹配 C500 后端的 MMA 路径；
- 0.1 ms 量级容易受 launch、同步和 CPU 调度影响。

因此先做 tile/warps 搜索和 profiler 观察，不应直接推翻在线 softmax 算法。

## 8. 常见故障速查

| 症状 | 常见原因 | 处理 |
| --- | --- | --- |
| `No module named torch` | 用了 `/usr/bin/python3` | 激活 `/opt/conda`，检查 `which python` |
| `libmpi.so.40` 缺失 | 未设置 MACA/OMPI 动态库路径 | 加载第 3.2 节环境变量 |
| `torch.cuda.is_available() == False` | 环境、设备节点或驱动问题 | 查 `mx-smi`、`/dev/mxcd`、`LD_LIBRARY_PATH` |
| 首次运行很慢 | Triton 正在 JIT | warmup 后再测，不把首次编译计入 |
| `OSError: could not get source code` | kernel 定义在 stdin/REPL | 保存到 `.py` 文件运行 |
| 准确率在 C500 错、海光对 | 后端 lowering、精度或布局差异 | 最小输入诊断，分别验证 load、算术、store，减少融合 |
| Python 直接段错误 | 后端编译器/运行时或非法访问 | 单题单进程复现；减小 tile；拆二维广播/归约；保留完整日志 |
| `mx-smi` 利用率总是 0% | kernel 太短、采样太慢 | 增大 repeat 或使用 profiler |
| 显存看似未释放 | PyTorch 缓存 allocator | 删除 tensor、`gc.collect()`、必要时 `empty_cache()`，同时看进程 |
| 结果波动 | JIT、频率、共享资源、CPU 调度 | 固定 warmup/repeat，多轮取中位数，记录设备状态 |

## 9. 推荐的每日工作流

```bash
# 1. 登录并进入持久化目录
cd /data/zk/kernelswift-2026-triton-kernels

# 2. 检查设备与环境
mx-smi
python -c "import torch,triton; print(torch.__version__,triton.__version__,torch.cuda.get_device_name(0))"

# 3. 修改前跑目标题短基线
python evaluator/auto_bench.py --v0_file REF --v1_file SOL --warmup 5 --repeat 10

# 4. 修改后先看正确性，再看短性能
# 5. 另一个终端连续观察
mx-smi --show-usage --show-memory --show-temperature -l 1000

# 6. 候选版本跑正式参数
python evaluator/auto_bench.py --v0_file REF --v1_file SOL --warmup 200 --repeat 500

# 7. 记录版本、参数、正确性、耗时和 mx-smi 状态
git status --short
```
